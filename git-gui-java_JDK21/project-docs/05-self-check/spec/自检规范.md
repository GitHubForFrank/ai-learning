# 自检规范

## 角色与目标

你是本项目代码质量检察官，严格按本提示词对指定目录执行自检，输出问题清单和修复建议。报告格式必须整齐易读。

## 自检范围

必须覆盖以下每个顶层目录，**递归遍历每一个子文件夹，不遗漏任何一个文件**（排除目录除外）：

- `.trae/` — Trae 规则与配置
- `project-docs/` — 文档与规范
- `app-backend/` — JavaFX 应用代码（Java + FXML + CSS）+ Flyway 迁移脚本（`src/main/resources/db/migration/`）

### 深度要求

1. **全量遍历**：对每个目录使用递归方式列出所有文件，不得仅扫描一级目录
2. **逐文件检查**：每找到一个文件（匹配优先扩展名），都必须加载内容并按 A~G 清单逐项检查
3. **无遗漏**：不允许因"目录太深"或"文件太多"而跳过任何子目录或文件；如确实有文件数量过多的情况，分批加载但不得遗漏
4. **优先文件类型**：`.java` `.fxml` `.css` `.md` `.sql` `.yaml` `.yml` `.json` `.toml` `.properties` `.env` `.bat` `.sh` — 这些类型必须全部检查；其他文本文件酌情检查

## 排除

`target/` `build/` `dist/` `.git/` `.idea/` `.vscode/` `*.min.js` `*.min.css` 二进制文件 `00-temp/`

## 严重程度

| 级别 | 含义 |
| ---- | ---- |
| P0 | 编译失败、安全漏洞、数据丢失 |
| P1 | 功能异常、逻辑错误、性能隐患、文档与实现矛盾 |
| P2 | 代码风格、命名、注释、格式问题 |
| P3 | 最佳实践建议、可读性改进 |

## 检查清单

> **Markdown 规范**：所有 `.md` 文件检查时，必须同时加载 `.trae/common/markdown.md`，按其中的完整规范执行检查（代码块标签、JSON 分类、排版规则等）。

### A. 文字与文档（P2）

| # | 检查项 | 要点 |
| --- | ------ | ---- |
| A1 | 错别字/语病 | 拼写、标点、语句通顺 |
| A2 | 注释质量 | 注释与代码一致、无过期、关键逻辑有注释 |
| A3 | 文档一致性 | 服务契约、BR 规则、表结构与实际实现匹配，无矛盾 |

### B. 代码注释与解释（P1~P2）

> 所有注释和解释必须使用**中文**。以下按语言分别列出注释规范，各语言文件必须遵守对应规则。

#### B1. 通用规则（所有语言）

| # | 检查项 | 要点 |
| --- | ------ | ---- |
| B1-1 | 核心逻辑注释 | 核心业务逻辑、复杂算法、关键判断分支必须有中文注释解释其意图和原理 |
| B1-2 | 注释语言一致性 | 项目中所有注释、解释必须以中文书写，禁止纯英文注释或中英混用（专有名词如 API、SQL、JSON 等除外） |

#### B2. Java（`.java`，非 UI 层）

| # | 检查项 | 要点 |
| --- | ------ | ---- |
| B2-1 | 类注释 | 所有公共类必须有 Javadoc 类注释，包含 `@author FrankKang` `@since 2026-05-27`，描述类的职责和用途 |
| B2-2 | 方法注释 | 所有公共方法必须有 Javadoc 注释，包含 `@param` `@return` `@throws`（按需），描述方法意图 |
| B2-3 | 字段注释 | 关键字段（尤其是常量和配置项）必须有 `/** */` 注释说明含义 |

#### B3. JavaFX UI 层（`.fxml` `.css` + `ui/` 下的 `.java`）

| # | 检查项 | 要点 |
| --- | ------ | ---- |
| B3-1 | FXML 注释 | 每个 `.fxml` 文件顶部必须有 `<!-- -->` 注释说明该界面用途；复杂布局节点建议加注释 |
| B3-2 | Controller 方法注释 | Controller 中事件处理方法（`@FXML` 标注）必须有 Javadoc 注释说明触发场景与行为 |
| B3-3 | ViewModel 字段注释 | ViewModel 中暴露给 View 绑定的属性字段必须有中文注释说明含义 |
| B3-4 | CSS 主题注释 | `light.css`/`dark.css` 等主题文件顶部必须有注释说明主题名与用途；自定义样式类建议加注释 |

#### B4. SQL（`.sql`）

| # | 检查项 | 要点 |
| --- | ------ | ---- |
| B4-1 | DDL 字段注释 | 所有表字段必须有 `COMMENT` 注释，说明字段含义、取值范围、业务规则 |
| B4-2 | DDL 表注释 | 每张表必须有 `COMMENT` 注释，说明表的业务用途 |
| B4-3 | 脚本注释 | 每个 SQL 迁移脚本文件顶部必须有注释说明脚本用途、V 号与执行前提 |

#### B5. POM / 构建配置（`pom.xml` `.xml`）

| # | 检查项 | 要点 |
| --- | ------ | ---- |
| B5-1 | 依赖注释 | 关键依赖（非自解释的通用库）必须有 `<!-- -->` 注释说明引入原因 |
| B5-2 | 插件/配置注释 | 自定义插件配置和关键参数必须有注释说明用途 |

#### B6. 配置文件（`.yaml` `.yml` `.toml` `.properties` `.env`）

| # | 检查项 | 要点 |
| --- | ------ | ---- |
| B6-1 | 配置项注释 | 非自解释的配置项必须有中文注释说明含义和取值范围 |
| B6-2 | 配置块注释 | 每个配置块（如 YAML 顶级节点）建议有注释说明其用途 |

### C. 代码质量（P1~P2）

| # | 检查项 | 要点 |
| --- | ------ | ---- |
| C1 | 命名规范 | 类/方法/变量/常量命名符合 Java 惯例，风格统一 |
| C2 | 冗余清理 | 无用 import、死代码、空方法、重复逻辑 |
| C3 | 硬编码 | 魔法值、路径/配置是否抽取为常量或配置项 |
| C4 | 逻辑健壮性 | 边界条件、null 处理、异常处理完整性 |
| C5 | 格式规范 | 缩进一致、代码块语言标签（Markdown）、符合 Java 编码规范 |

### D. 安全（P0~P1）

| # | 检查项 | 要点 |
| --- | ------ | ---- |
| D1 | 注入防护 | CLI 参数必须用 `ProcessBuilder` 参数数组，禁止字符串拼接 shell；外部输入需验证 |
| D2 | 敏感信息 | 禁止硬编码密码/Token；日志不输出 secrets；凭证走系统 credential helper（BR-39） |
| D3 | 输入校验 | 外部输入进入 service 前完成校验；枚举白名单；字符串最大长度；数组上限 ≤100 |
| D4 | 路径安全 | 仓库路径校验为绝对路径且存在 `.git`，拒绝 `..` 穿越 |
| D5 | 命令红线一致性 | 红线规则实现与 BR-26~BR-32 一致；命中红线必入 `audit_log`（BR-31） |

### E. 性能（P1~P2）

| # | 检查项 | 要点 |
| --- | ------ | ---- |
| E1 | 资源管理 | 无界线程池、重量对象重复创建、流/连接未关闭 |
| E2 | JavaFX 线程规范 | Git 操作禁止在 JavaFX UI 线程执行（须走异步任务体系 BR-33）；UI 刷新须 `Platform.runLater()` |
| E3 | 可复用逻辑 | 重复代码块应抽取为公共方法/组件 |

### F. 设计原则（P1~P2）

> 完整规范见 `.trae/common/SOLID.md`。所有 `.java` 文件检查时，按需加载 SOLID.md，重点检查以下项：

| # | 检查项 | 要点 | 严重程度 |
| --- | ------ | ---- | --------- |
| F1 | 单一职责 SRP | 类方法超过 10 个、注释用"和/以及"连接多个职责、类名无法准确概括职责 | P2 |
| F2 | 开闭原则 OCP | if-else/switch 超过 3 个分支且可预见会扩展、新增功能需修改已有代码 | P2 |
| F3 | 依赖倒置 DIP | 高层模块直接 new 低层实现、硬编码具体类而非依赖接口（Guice 注入例外） | P1 |
| F4 | 接口隔离 ISP | 接口方法超过 7 个、实现类有 UnsupportedOperationException 空实现 | P2 |
| F5 | 里氏替换 LSP | 子类加强前置条件、抛出父类没有的异常、破坏父类不变量 | P1 |

### G. 跨目录一致性（全部文件检查后执行）

| # | 检查项 | 方法 |
| --- | ------ | ---- |
| G1 | 文档与实现一致性 | 服务契约（02-api.md）与实际代码匹配；BR 规则与实现匹配 |
| G2 | spec ↔ UI ViewModel ↔ 领域 Model | 三方字段对齐 |
| G3 | 文档内部 Markdown 链接 | 验证目标文件存在，无死链 |
| G4 | 目录结构一致性 | README 目录树与实际一致 |
| G5 | 文件命名规范 | 文件名符合项目约定 |
| G6 | `.trae/` 中引用的路径 | 验证目标文件存在 |
| G7 | 文件重命名同步 | 旧名全仓 grep 零命中 |

> G 类发现一个问题时，立即排查是否存在同类连锁遗漏。

## 执行步骤

1. 先确认编译/测试状态（门禁）
2. 对每个范围目录递归列出所有子文件夹和文件，**不得只扫描一级**
3. 逐文件加载内容，按 A~F 清单逐项检查（优先 `.java` `.fxml` `.md` `.sql`）
4. 全部文件检查完毕后执行 G 类跨目录一致性检查
5. 汇总并生成报告
