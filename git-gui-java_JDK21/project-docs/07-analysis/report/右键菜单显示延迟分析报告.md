# 右键菜单显示延迟分析报告

## 问题背景

用户反馈：侧边栏仓库列表右键菜单"总是显示延迟"，并给出 4 条优化建议征求评估意见。

本文基于代码静态分析，定位延迟根因，并逐条评估 4 条建议的适用性与收益。

## 当前实现分析

### 右键触发流程

右键菜单由 [MainController.attachContextMenu()](file:///d:/workspaces/workspace_gitee/software-development-kit/git-gui-java_JDK21/app-backend/src/main/java/com/gitgui/ui/main/MainController.java#L774-L804) 注册，核心流程如下：

```java
listView.setOnContextMenuRequested(event -> {
    RepoListItem item = pickItemAt(listView, event.getX(), event.getY()); // 内存计算
    if (item == null) { sharedContextMenu.hide(); return; }
    listView.getSelectionModel().select(item);                            // 内存操作
    rebuildRepoContextMenu(item);                                         // 重建菜单项
    sharedContextMenu.hide();
    sharedContextMenu.show(listView, event.getScreenX(), event.getScreenY()); // 显示
    event.consume();
});
```

### rebuildRepoContextMenu 做了什么

[rebuildRepoContextMenu()](file:///d:/workspaces/workspace_gitee/software-development-kit/git-gui-java_JDK21/app-backend/src/main/java/com/gitgui/ui/main/MainController.java#L950-L1051) 每次右键都会被调用，执行内容如下：

| 步骤 | 操作 | 类型 | 耗时量级 |
| ---- | ---- | ---- | -------- |
| 1 | `getItems().clear()` | ObservableList 清空 | 内存 |
| 2 | `new MenuItem(...)` × 9 | 创建 9 个菜单项对象 | 内存 |
| 3 | `new SeparatorMenuItem()` × 2 | 创建 2 个分隔符 | 内存 |
| 4 | `I18nUtil.get(...)` × 11 | 国际化文案查找 | 内存 |
| 5 | `setOnAction(e -> {...})` × 11 | 设置 lambda 回调 | 内存 |
| 6 | `getItems().add(...)` × 11 | 添加到 ObservableList | 内存 |

### I18nUtil.get 的开销

[I18nUtil.get()](file:///d:/workspaces/workspace_gitee/software-development-kit/git-gui-java_JDK21/app-backend/src/main/java/com/gitgui/ui/i18n/I18nUtil.java#L38-L40) 的实现如下：

```java
private static volatile ResourceBundle bundle =
        ResourceBundle.getBundle(BASE_NAME, Locale.SIMPLIFIED_CHINESE);

public static String get(String key) {
    return bundle.getString(key);
}
```

ResourceBundle 在类加载时一次性初始化（静态变量），`get()` 仅做 `bundle.getString(key)` 内存查找，无磁盘 IO。

## 延迟根因定位

### 代码层面：全程内存操作，无 IO

对 `rebuildRepoContextMenu` 的完整执行路径逐行审查，结论如下：

- 没有 `.git` 目录读取
- 没有数据库查询
- 没有 git 命令执行
- 没有网络请求
- 没有 `Platform.runLater` 异步等待
- 所有数据来自 `RepoListItem` 的内存属性

11 个 MenuItem 的创建 + 文案查找 + lambda 设置，整体耗时预估 **< 1ms**，不构成用户可感知的延迟。

### 真正延迟来源：JavaFX ContextMenu.show() 框架开销

用户感知的"延迟"主要来自 `sharedContextMenu.show()` 触发的 JavaFX 框架层工作：

| 阶段 | 说明 | 耗时量级 |
| ---- | ---- | -------- |
| PopupWindow 创建 | ContextMenu 基于 PopupWindow 实现 | 10-30ms |
| CSS 样式计算 | 对 11 个 MenuItem 应用样式表 | 10-20ms |
| 布局测量 | 测量每个 MenuItem 的 prefWidth/prefHeight | 5-15ms |
| 场景图更新 | 构建 Scene、触发 pulse | 5-10ms |
| 渲染提交 | 提交到 Glass 窗口系统渲染 | 5-10ms |

首次右键的延迟会更高（冷启动需加载 ContextMenu skin、初始化 CSS），后续右键因 skin 缓存会略快，但仍受 CSS + 布局 + 渲染开销制约。

此外，若 ListView 正在进行 cell 回收或重绘（仓库列表项较多时），右键事件会在事件队列中排队，进一步推迟菜单显示。

## 四条优化建议逐条评估

### 建议 1：菜单结构预缓存

> 菜单结构预缓存：右键菜单选项是固定的，提前构建好菜单对象，右键时仅做显示，不重新生成

**评估**：⚠️ **方向正确，但收益微小**

| 维度 | 分析 |
| ---- | ---- |
| 当前开销 | 每次右键创建 11 个 MenuItem，耗时 < 1ms |
| 预缓存后 | 复用 MenuItem，仅更新 favoriteItem 文案，耗时 < 0.1ms |
| 用户感知 | 节省 < 1ms，完全感知不到 |
| 实施成本 | 中等——需把 setOnAction 中的局部变量 `path`/`item` 改为引用字段 `contextMenuTargetItem`，并处理文案更新 |
| 风险 | 低——MenuItem 复用在 JavaFX 中是安全的 |

**结论**：可以作为代码质量改进（减少对象创建、降低 GC 压力），但**不能解决延迟问题**。

### 建议 2：状态异步加载

> 状态异步加载：如果菜单项需要显示仓库状态（如是否有变更），改为异步回填，先出菜单再刷新状态

**评估**：❌ **不适用**

当前 11 个 MenuItem 全部是**固定文案**（提交/拉取/推送/获取/切换分支/收藏/设置别名/修改远程 URL/在文件管理器中打开/复制路径/刷新此仓库），没有任何一项依赖仓库状态（如"是否有变更""当前分支名"等）。

唯一的动态文案是 favoriteItem（"收藏" / "取消收藏"），但其数据来源是 `item.isFavorite()`——一个内存 boolean 属性，不是 IO 操作。

**结论**：当前菜单无状态加载需求，此建议无落地场景。

### 建议 3：去掉右键时的 IO 操作

> 去掉右键时的 IO 操作：不要在右键触发瞬间去读 .git 目录、查配置等磁盘操作

**评估**：❌ **不适用**

经逐行审查，`rebuildRepoContextMenu` 和 `attachContextMenu` 的完整代码路径中**不存在任何 IO 操作**：

- 无 `.git` 目录读取
- 无 `git` 命令调用
- 无数据库查询
- 无配置文件读取
- 无网络请求

所有数据均来自 `RepoListItem` 的内存属性和 `I18nUtil` 的内存缓存。

**结论**：当前代码已经满足"无 IO"要求，此建议无优化空间。

### 建议 4：防抖 / 合并触发

> 防抖 / 合并触发：避免快速右键多次触发重复计算

**评估**：⚠️ **价值微弱**

当前代码已通过 `sharedContextMenu.hide()` + `show()` 处理快速连续右键（[L790-L793](file:///d:/workspaces/workspace_gitee/software-development-kit/git-gui-java_JDK21/app-backend/src/main/java/com/gitgui/ui/main/MainController.java#L790-L793)，注释提到修复 issue #1：菜单叠加）。

由于 `rebuildRepoContextMenu` 本身耗时 < 1ms，"重复计算"的代价可以忽略。防抖的主要价值是减少 `show()` 的框架开销，但防抖会引入额外延迟（等待防抖窗口），反而可能让单次右键更慢。

**结论**：当前实现已足够，防抖属于过度设计。

## 我的意见

### 总体判断

**4 条建议中，没有一条击中真正的延迟根因。**

| 建议 | 评估 | 能否解决延迟 |
| ---- | ---- | ------------ |
| 1. 菜单结构预缓存 | 方向正确，收益 < 1ms | ❌ 不能 |
| 2. 状态异步加载 | 不适用（菜单无状态加载） | ❌ 不适用 |
| 3. 去掉右键时 IO | 不适用（代码已无 IO） | ❌ 不适用 |
| 4. 防抖 / 合并触发 | 价值微弱，可能适得其反 | ❌ 不能 |

真正的延迟来自 **JavaFX `ContextMenu.show()` 的框架层开销**（CSS 计算 + 布局测量 + 场景图更新 + 渲染），这是应用层难以直接优化的。

### 延迟量级待确认

"总是显示延迟"是一个主观描述，需要先量化：

- 如果延迟是 **50-100ms**：属于 JavaFX ContextMenu 的正常框架开销，与同类应用（IntelliJ IDEA、TortoiseGit）相当，无需优化
- 如果延迟是 **200-500ms**：可能存在事件循环阻塞（如 ListView cell 回收、后台任务抢占），需要排查
- 如果延迟是 **> 500ms**：属于异常，可能有隐藏的同步阻塞点

## 推荐优化方案

### 第一步：测量延迟（必做）

在 `rebuildRepoContextMenu` 前后和 `show` 前后插入耗时测量，确认延迟到底发生在哪个阶段：

```java
listView.setOnContextMenuRequested(event -> {
    long t0 = System.nanoTime();
    RepoListItem item = pickItemAt(listView, event.getX(), event.getY());
    if (item == null) { sharedContextMenu.hide(); return; }
    listView.getSelectionModel().select(item);
    long t1 = System.nanoTime();
    rebuildRepoContextMenu(item);
    long t2 = System.nanoTime();
    sharedContextMenu.hide();
    sharedContextMenu.show(listView, event.getScreenX(), event.getScreenY());
    long t3 = System.nanoTime();
    log.info("右键菜单耗时：pick={}μs rebuild={}μs show={}μs total={}μs",
            (t1-t0)/1000, (t2-t1)/1000, (t3-t2)/1000, (t3-t0)/1000);
    event.consume();
});
```

根据测量结果决定是否需要优化，以及优化哪个阶段。

### 第二步：预缓存 MenuItem（可选，建议 1 的正确实施）

如果测量确认 `rebuild` 阶段有可观开销，或希望减少 GC 压力，可实施预缓存：

```java
// 字段：预构建 MenuItem（initialize 时创建一次）
private final MenuItem commitItem = new MenuItem(I18nUtil.get("sidebar.repo.contextMenu.commit"));
private final MenuItem pullItem = new MenuItem(I18nUtil.get("sidebar.repo.contextMenu.pull"));
// ... 其余 9 个 MenuItem 同理

// initialize 时设置 setOnAction（lambda 引用 contextMenuTargetItem 字段）
commitItem.setOnAction(e -> {
    sharedContextMenu.hide();
    setCurrentRepo(contextMenuTargetItem.getRepoPath());
    onCommit();
});

// 右键时仅更新 favoriteItem 文案，不重建
private void showRepoContextMenu(RepoListItem item) {
    contextMenuTargetItem = item;
    favoriteItem.setText(item.isFavorite()
            ? I18nUtil.get("sidebar.repo.unfavorite")
            : I18nUtil.get("sidebar.repo.favorite"));
    sharedContextMenu.hide();
    sharedContextMenu.show(...);
}
```

### 第三步：减少菜单项数量（可选）

当前菜单有 9 个 MenuItem + 2 个分隔符。JavaFX ContextMenu 的 CSS/布局开销与菜单项数量正相关。如果测量确认 `show` 阶段是瓶颈，可考虑：

- 将低频操作（修改远程 URL、复制路径）合并到二级菜单
- 或移除冗余项（参考已有的《仓库列表右键菜单精简分析报告》）

## 结论

1. **4 条建议均未击中真正的延迟根因**。建议 2、3 基于错误假设（菜单无状态加载、无 IO 操作），建议 1、4 方向正确但收益微小
2. **真正的延迟来自 JavaFX `ContextMenu.show()` 的框架开销**，不是应用代码
3. **建议先测量延迟量级**，再决定是否优化。50-100ms 属于正常框架开销，无需处理
4. 如果确实需要优化，**预缓存 MenuItem（建议 1）是唯一有价值的方向**，但预期收益 < 1ms，用户感知不到
