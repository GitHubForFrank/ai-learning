# Core Rules — 全局核心规则 — 最高优先级

> 本文是共享基座。项目专属规则在 `project-docs/00-spec/` 中。
> 项目级 spec 与本文档冲突时，项目级 spec 优先。
> 项目内部 spec 冲突时优先级：**项目 00-core.md > 项目 01-domain.md > 项目 02-api.md（服务契约）> 项目 03-backend.md / 项目 05-frontend.md > 局部业务规则**。

---

## 1. SDD 强制开发流程

**设计 → 数据库 → 后端 → UI**，顺序不可逆（桌面应用 UI 与后端同处一个 `app-backend/` 模块，但实现仍有先后）：

```plaintext
① 规约先行：BR-* / 服务契约 / 数据字典先定稿（修改 spec/）
② 建表迁移：DDL 脚本写入 app-backend/src/main/resources/db/migration/，V 号递增
③ 后端实现：领域层 → 应用层 → 基础设施层（CLI/SQLite），严格按 DDD 分层
④ UI 实现：FXML → Controller → ViewModel → 调用服务接口（对齐服务契约）
```

**严禁**：

- ❌ 先写代码后补规则
- ❌ 私自修改规约不同步到全模块（Entity / Model / UI ViewModel / 迁移脚本 / 文档）
- ❌ 跨步骤跳过（如跳过 DB 迁移直接写后端服务）

### 1.1 Spec 变更传播工作流

当 spec 中的 BR 规则、实体字段或服务契约发生变更时，必须在全模块同步更新：

```plaintext
① 修改 BR / 实体字段（01-domain.md）
② 检查受影响服务契约，更新 02-api.md
③ 生成/修改迁移脚本，V 号递增（app-backend/src/main/resources/db/migration/）
④ 更新后端 Entity/Model/Service/Repository，[SPEC: ...] 注释标记
⑤ 更新 UI 层 ViewModel/服务调用，[SPEC: ...] 注释标记
⑥ 更新相关测试用例，标注覆盖的 BR 编号
⑦ 更新 CHANGELOG
```

**严禁**：

- ❌ 修改 BR 后不检查下游影响
- ❌ 服务契约变更不同步更新 UI 调用方

## 2. Task 编号体系 — 轻量追溯

**定位**：Task 编号仅用于代码追溯，不做任务管理、不做状态跟踪、不做看板。

**格式**：`Task<NNN>`，三位数字，从 001 开始连续递增，不复用。

**何时分配**：每次 AI IDE 执行开发任务时，自动分配一个新的 Task 编号。

**标注位置**：同一 Task-ID 在以下位置必须一致：

| 位置 | 格式示例 |
| ------ | --------- |
| 迁移脚本头注释 | `-- [TASK: Task001]` |
| Java/FXML 代码追溯注释 | `// [TASK: Task001][SPEC: project-docs/00-spec/project/02-api.md §3]` |
| CHANGELOG 条目 | `- Task001：{功能描述}` |

**不需要的**：

- ❌ Task 状态表 / 看板 / 进度跟踪
- ❌ Task 与 PR/MR 关联
- ❌ Task 文档 / 工作量评估

## 3. 代码追溯注释规范

所有实现了 spec 条款的关键代码**必须**标注来源：

```java
// [TASK: Task001][SPEC: {domain-spec-file} §{section} {BR-id}] {功能描述}
```

格式：`[TASK: Task<NNN>][SPEC: <文件> §<章节> <BR-id>] {功能描述}`

### 3.1 Spec 间引用规范

spec 文件之间相互引用时，统一使用以下格式：

| 引用类型 | 格式 | 示例 |
| ------ | ------ | ------ |
| 引用其他 spec 文件的章节 | `参见 [{file} §{section}]` | `参见 [01-domain.md §BR-03]` |
| 引用其他 spec 文件的实体 | `参见 [{file} §{Entity}]` | `参见 [01-domain.md §Favorite]` |
| 同文件内 BR 互引 | `BR-{NN} 制约 BR-{MM}` | `BR-08 制约 BR-26 的推送红线` |
| 引用外部标准 | `遵循 [{标准名}]({url})` | `遵循 [Keep a Changelog](https://keepachangelog.com/)` |

## 4. 文档管理约定

### 4.1 README.md 约定

#### 4.1.1 README 的定位

根目录 `README.md` 的唯一职责：让初次接触项目的人快速了解项目是什么、目录是什么、怎么启动。

#### 4.1.2 必须包含

| 内容              | 说明                          |
| ----------------- | ----------------------------- |
| 项目一句话定位         | 产品是什么、解决什么问题                |
| 技术概况            | 架构模式、语言、核心依赖（不展开细节）         |
| **顶层目录结构**（仅一级） | 每个顶层目录的用途，不展开到二级以下          |
| 本地启动步骤          | 前置条件 + 命令 + 验证命令            |
| 文档索引            | "我想了解 X → 去哪个文件看"（链接，不搬运内容） |

#### 4.1.3 禁止包含

| 禁止                    | 原因                                     |
| ----------------------- | ---------------------------------------- |
| 开发细节（类名、配置项、SQL、路径说明） | 属于 spec，README 只做指路牌                   |
| 服务契约 / 业务规则         | 属于 spec                                  |
| 二级以下目录展开              | 子目录自有 README                           |
| `00-temp/` 子目录细节      | 临时目录，见 4.3 节隔离原则                        |

#### 4.1.4 触发更新的事件

| 事件           | 操作                     |
| -------------- | ------------------------ |
| 新增 / 删除顶层目录  | 更新目录结构代码块              |
| 启动方式变化        | 更新启动步骤                 |
| 新增重要 spec 文档 | 更新文档索引                 |

#### 4.1.5 完成判定

- [ ] README 目录树与实际目录一致（无幽灵目录、无遗漏）
- [ ] 每个顶层目录至少出现一次
- [ ] 不在 README 中展开 `00-temp/` 子目录细节

### 4.2 CHANGELOG.md 约定

#### 4.2.1 定位

`CHANGELOG.md` 位于项目根目录，是**项目变更的唯一可读轨迹**，遵循 [Keep a Changelog](https://keepachangelog.com/zh-CN/1.1.0/) 格式。

#### 4.2.2 何时更新

| 场景                | 操作                            |
| ------------------- | ------------------------------- |
| 功能完成（可用）          | `[Unreleased]` 段追加 `Added` 条目 |
| Bug 修复            | `Fixed` 条目，简述问题和影响范围          |
| 服务契约 / 数据结构变更      | `Changed` 条目，说明变更前后差异         |
| typo / 格式化 / 注释调整 | **不入 CHANGELOG**              |

#### 4.2.3 格式

```markdown
## [Unreleased]

### Added

- Task001：{功能描述}

### Changed

- Task002：{变更描述}

### Fixed

- {修复描述}
```

分类（按优先级）：`Added` / `Changed` / `Deprecated` / `Removed` / `Fixed` / `Security`

#### 4.2.4 发布时

将 `[Unreleased]` 改为版本号和日期，并添加新的空 `[Unreleased]`：

```markdown
## [1.0.0] - 2026-07-01

## [Unreleased]
```

#### 4.2.5 Git 使用原则 — 桌面 Git 客户端特别约定

> 本产品是图形化 Git 客户端，**对用户选定的工作目标仓库执行 Git 操作是产品的核心功能**。因此旧规则「严禁应用执行任何 git 命令」不再适用，需按以下范围重新界定。

**允许**：

- ✅ 应用对**用户在 UI 中选定的工作目标仓库**执行 Clone/Commit/Pull/Push/Rebase 等全部 Git 操作
- ✅ 应用通过本地 Git 命令行（CLI）操作目标仓库
- ✅ 操作目标仓库的命令轨迹记录到 `operation_log` 与 `audit_log`

**严禁**：

- ❌ 应用对**自身项目代码仓库**执行 `git commit` / `git add` / `git push` 等自动提交
- ❌ 用 `git log` 读取自身项目变更历史（改读 CHANGELOG.md）
- ❌ 在产品功能中提供「对应用自身仓库生成 git 提交信息」的命令

> 应用自身代码仓库的 git 提交由开发者人工校验后手动完成；变更轨迹通过 CHANGELOG 记录。

### 4.3 文件重命名 → 同步引用

#### 4.3.1 触发时机

- 任何文件 / 目录被移动或重命名
- 任何 Markdown 标题、章节锚点被改写

#### 4.3.2 必须执行的步骤 — 按顺序

1. 用搜索工具全仓扫描旧名（包含路径片段、文件 stem、章节锚点）
2. 同步更新所有命中位置：
    - `README.md` 的目录树和正文引用
    - 其他 `.md` 文档的相对链接
    - 代码注释、配置文件中的硬编码路径
    - 同目录或父目录的 `index.md` / `SUMMARY.md`（若存在）
3. 二次扫描旧名，确认 **0 命中**

#### 4.3.3 完成判定

- [ ] 旧名全仓 grep 结果为空
- [ ] README 目录树与实际结构一致
- [ ] 所有相对链接可正常跳转

#### 4.3.4 反例

- ❌ 只 `mv` 文件不改引用 → 文档死链
- ❌ 只改 README，漏掉子目录内的引用

### 4.4 临时目录隔离原则

#### 4.4.1 适用对象

`00-temp/` 及所有标注为「草稿 / 试验 / WIP」的目录。

#### 4.4.2 规则

| 规则           | 说明                                            |
| -------------- | ----------------------------------------------- |
| README 只暴露顶层 | `README.md` 目录树只列 `00-temp/` 本身，不展开子目录        |
| 单向依赖         | 正式目录**禁止引用** `00-temp/` 内容；`00-temp/` 可引用正式目录 |
| 不进规则 / 指南    | 规则文档不允许出现 `00-temp/` 路径                       |

#### 4.4.3 转正流程

1. 在 `00-temp/` 内确认内容稳定
2. 选定目标正式目录
3. 移动文件 → 触发 4.3 节「重命名同步」规则
4. 删除 `00-temp/` 下的原文件

#### 4.4.4 完成判定

- [ ] README 中 `00-temp/` 仅占一行，无子目录展开
- [ ] 正式目录下 grep `00-temp/` 结果为空

### 4.6 指南 / 安装文档规范

#### 4.6.1 适用对象

安装指南、快速上手、README 的 Setup 段落、任何含安装命令的文档。

#### 4.6.2 必须遵守

**安装步骤必带 verify**：每个 `install` / `add` 类命令后，紧跟一条可观察的校验命令：

```bash
# ✅ 正确
mvn clean compile
java -version   # verify

# ❌ 错误：装完没有校验
mvn clean compile
```

**命令块必须标明执行目录**：每个代码块开头要么 `cd <path>`，要么注释标明：

```bash
# 在 app-backend/ 下执行：
mvn javafx:run
```

**跨步骤切换目录要重新声明**，不依赖读者记忆。

#### 4.6.3 完成判定

- [ ] 所有 install 命令下一行都有可观察的 verify
- [ ] 所有命令块前 3 行内能让读者明确执行目录
- [ ] verify 命令的预期输出 / 退出码有说明

## 5. 调试与交付门禁

### 5.1 标准调试流程

```bash
# Step 1: 确认单实例锁已清理（上次异常退出可能残留）
ls ~/.git-gui/.git-gui.lock 2>/dev/null && rm ~/.git-gui/.git-gui.lock

# Step 2: 编译 + 测试
cd app-backend
mvn clean compile -q
mvn test

# Step 3: 启动应用
mvn javafx:run
```

### 5.2 门禁规则 — 不可绕过

| 规则 | 说明 |
| ------ | ------ |
| `mvn compile` 零错误 | 主代码编译无错误 |
| `mvn test` 全通过 | 测试类命名 `*Test.java`（单元）/ `*UiTest.java`（JavaFX）；严禁日常使用 `-DskipTests`，仅限紧急场景 |
| 单实例锁正常 | 应用退出后锁文件必须释放，否则下次启动无法聚焦已有窗口 |

> 数据目录、DB 路径、锁文件路径等配置见各项目 `project-docs/00-spec/project/project.yml`。

## 6. 安全约束 — 全局

### 6.0 安全需求矩阵

| 安全需求 | 全局约束 | 后端实现参考 | 验证方式 |
| ------ | ------ | ------ | ------ |
| 命令注入防护 | §6.2 | 参见 [03-backend.md §安全约束] | 代码审查 |
| Secrets 管理 | §6.3 | 参见 [03-backend.md §安全约束] | 扫描工具 |
| 命令红线管控 | §6.4 | 参见 [03-backend.md §命令红线拦截器] + [01-domain.md §BR-26~BR-32] | 测试 + 审计日志 |
| 路径安全 | §6.2 | 参见 [03-backend.md §安全约束] | 代码审查 |

### 6.1 输入校验

- 所有外部输入（用户在 UI 输入的路径、URL、分支名、commit message 等）**必须**在进入 service 层前完成校验
- 枚举类型用白名单；字符串字段必须有显式最大长度
- 列表参数必须有上限（如多仓库检索深度 ≤ 10，文件列表 ≤ 10000）

### 6.2 注入防护 / 路径安全

- Git 命令行调用**必须**使用 `ProcessBuilder` 参数数组，**严禁**字符串拼接 shell，防止命令注入
- SQL **必须**用参数化查询；**严禁**字符串拼接
- 文件路径操作必须校验为绝对路径且拒绝 `..` 穿越越界
- 仓库路径必须存在 `.git` 目录

### 6.3 Secrets 管理

- **严禁**任何 secrets 提交进代码仓
- **严禁**在日志中输出 secrets 原文（Git 凭证、SSH 密钥内容、用户密码）
- **严禁**硬编码 API Key / 密码
- Git 凭证通过系统 credential helper 管理，应用不明文存储密码；SSH 密钥仅存储路径不存密钥内容

### 6.4 命令红线管控

> 详见 [01-domain.md §BR-26~BR-32]。高风险 Git 操作（裸 force push、向保护分支 force push、推送敏感文件、推送到非授权远程、`--no-verify` 等）命中红线时**拦截阻断**或**强制二次确认**，并记录到 `audit_log`。红线规则、保护分支清单、远程白名单、敏感文件规则在 Settings 中配置。

## 7. 绝对禁止项（汇总）

### 7.1 代码操作禁止

- ❌ 应用对自身项目代码仓库执行 `git commit` / `git push`（参见 §4.2.5）
- ❌ 修改已合入的迁移脚本
- ❌ 提交代码中保留 `System.out.println` 调试输出
- ❌ 硬编码 API Key / 密码等 secrets
- ❌ 在 JavaFX Application Thread 执行 Git 操作（会冻结 UI）

### 7.2 安全禁止

- ❌ Git 命令行字符串拼接 shell（必须用 `ProcessBuilder` 参数数组）
- ❌ 日志输出 Git 凭证 / SSH 密钥原文 / PII
- ❌ 跳过命令红线拦截器直接执行高风险 Git 操作

> 技术选型禁止清单见各项目 `project.yml`。
