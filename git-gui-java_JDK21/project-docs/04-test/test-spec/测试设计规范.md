# 测试体系设计规范

> 本文是项目测试体系的总体设计规范，涵盖目录结构、公共工具、测试分层、报告模板等。
> 本规范与技术栈无关，以 PowerShell 为示例语言，项目可根据实际技术栈替换实现方式。
>
> **本项目落地**：git-gui 按本模板落地为 `test-unit/`（JUnit5 + Mockito）+ `test-ui/`（TestFX），具体见 [../README.md](../README.md)。本文保留通用模板内容供跨项目复用。

---

## 1. 测试体系概览

### 1.1 测试分层

```plaintext
          ┌──────────────────┐
          │    test-e2e      │  ← 前后端联调（带页面截图验证）
          ├──────────────────┤
          │    test-api      │  ← 纯 API 接口自动化（无前端参与）
          ├──────────────────┤
          │   test-common    │  ← 全局公共依赖（所有测试共用）
          └──────────────────┘
```

- **test-api**：通过脚本/代码直接调用后端 API，验证接口契约，无需启动前端。
- **test-e2e**：通过浏览器自动化工具操控前端页面，结合截图验证前后端联调效果。
- **test-common**：抽取所有测试共用的工具方法、配置、日志，避免重复。

### 1.2 目录结构

```plaintext
test/
├── README.md                        # 测试体系总规范、执行入口、环境说明
├── test-common/                     # 全局公共依赖
│   ├── config.global.*              # 全局环境配置（地址、超时、浏览器参数等）
│   ├── common-http.*                # 通用 HTTP 请求工具
│   ├── common-assert.*              # 通用断言校验工具
│   ├── common-log.*                 # 统一日志打印工具
│   ├── common-screenshot.*           # 浏览器操控 + 自动截图工具（联调专用）
│   └── README.md                    # 工具方法使用说明文档
├── test-api/                            # 第一层：纯 API 接口自动化测试
│   ├── run-all.*                        # API 测试总执行入口
│   └── TC-API-{NN}-{功能描述}/          # 每个用例一个子目录
│       ├── TC-API-{NN}-{功能描述}.md     # 用例说明（必须）
│       ├── TC-API-{NN}-{功能描述}.{ext}  # 执行脚本（可选）
│       └── output/                      # 执行产出（执行后自动生成）
│           └── YYYYMMDD_HHMMSS/
│               ├── request-body.json
│               ├── response-body.json
│               └── test.log
├── test-e2e/                            # 第二层：前后端联调测试
│   ├── run-all.*                        # E2E 测试总执行入口
│   └── TC-E2E-{NN}-{功能描述}/          # 每个用例一个子目录
│       ├── TC-E2E-{NN}-{功能描述}.md     # 用例说明（必须）
│       ├── TC-E2E-{NN}-{功能描述}.{ext}  # 执行脚本（可选）
│       └── output/                      # 执行产出（执行后自动生成）
│           └── YYYYMMDD_HHMMSS/
│               ├── TC-E2E-{NN}-001.png   # 步骤截图
│               ├── TC-E2E-{NN}-002.png
│               └── test.log
└── test-report/             # 全局汇总报告归档目录
    └── YYYYMMDD_HHMMSS.md           # 每次执行的报告（按时间戳命名）
```

### 1.3 技术栈适配

本规范以 PowerShell 为示例语言，但核心原则（分层、公共依赖抽取、报告模板）与语言无关。项目可根据技术栈替换实现方式：

| 能力 | PowerShell 示例 | 等价替代 |
| ---- | -------------- | ------- |
| HTTP 封装 | `Invoke-Api` | pytest + httpx / fetch / axios |
| 断言 | `Assert-Equal` | `assert` / `expect` / chai |
| 日志 | `Write-Log` | `logging` / `console.log` / winston |
| 浏览器操控 | `Save-Screenshot` 等截图工具 | Playwright / Cypress / Selenium |
| 脚本入口 | `run-all.ps1` | `Makefile` / `npm scripts` / `pytest` |

## 2. test-common — 全局公共依赖

> **模块实现优先级**：以下模块可按项目成熟度渐进实现，不必一次性全部到位。

| 模块 | 优先级 | 说明 |
| ---- | ------ | ---- |
| `config.global.*` | P0（必须） | 配置与代码分离的基础，所有脚本依赖 |
| `common-log.*` | P0（必须） | 统一日志输出，所有脚本依赖 |
| `common-assert.*` | P1（推荐） | 语义化断言，可暂用语言原生断言替代 |
| `common-http.*` | P1（推荐） | HTTP 封装，可暂用语言原生 HTTP 客户端替代 |
| `common-screenshot.*` | P2（E2E 专用） | 仅 E2E 测试需要 |

### 2.1 全局环境配置

集中管理所有测试共用的环境变量。

**必须包含的配置类别**：

| 类别 | 说明 | 示例 |
| ---- | ---- | ---- |
| 服务地址 | 后端 API 地址、前端页面地址 | `http://localhost:8080` |
| 测试数据 | 测试用账号、Token 等 | 测试用认证凭证 |
| 超时配置 | HTTP 请求超时、浏览器操作超时 | 30s / 10s |
| 截图配置 | 截图保存目录、格式 | png |
| 日志级别 | Debug / Info / Warn / Error | Info |

**规则**：

- 禁止在测试脚本中硬编码地址、端口、密钥，统一从配置文件读取
- 可通过命令行参数覆盖，参数优先级高于配置文件
- 敏感信息不得提交到版本库，本地使用 `.gitignore` 排除的覆盖文件管理

**配置示例**（PowerShell，仅供参考，具体变量名由项目自定义）：

```powershell
# config.global.ps1 — 全局环境配置（示例）
$script:BaseUrl        = "http://localhost:8080"    # 后端 API 地址
$script:FrontendUrl    = "http://localhost:3000"    # 前端页面地址
$script:TestCredential = "{测试用凭证}"              # 认证凭证（如 API Key、JWT Token、Basic Auth 等）
$script:HttpTimeout    = 30                          # HTTP 超时（秒）
$script:BrowserTimeout = 10                          # 浏览器超时（秒）
$script:ScreenshotDir  = ""                          # 运行时由调用方设置
$script:LogLevel       = "Info"                      # 日志级别
```

**配置文件格式约定**：

- 推荐使用结构化格式（JSON / YAML / TOML）作为主配置文件，便于跨语言解析和 CI/CD 集成
- 脚本/代码文件仅负责加载和命令行参数覆盖，不直接存储配置值
- 敏感信息通过独立文件覆盖（如 `config.local.json`），该文件加入 `.gitignore`
- 项目可按技术栈选择具体格式，核心要求是**配置与代码分离**

**配置示例**（JSON，跨语言通用）：

```json
{
  "baseUrl": "http://localhost:8080",
  "frontendUrl": "http://localhost:3000",
  "testCredential": "{测试用凭证}",
  "httpTimeout": 30,
  "browserTimeout": 10,
  "screenshotDir": "",
  "logLevel": "Info"
}
```

### 2.2 通用 HTTP 请求工具

封装底层 HTTP 调用，提供统一的请求、响应处理、错误捕获。

**必须提供的能力**：

| 函数 | 职责 | 返回值必须包含 |
| ---- | ---- | -------------- |
| `Invoke-Api` | 发送普通 HTTP 请求 | `StatusCode`、`Content`、`Error` |

**可选扩展能力**（仅当被测系统支持流式响应时提供）：

| 函数 | 职责 | 返回值必须包含 |
| ---- | ---- | -------------- |
| `Invoke-ApiSse` / `Invoke-StreamApi` | 发送流式请求（SSE/WebSocket 等） | `StatusCode`、`Events`（事件列表）、`HasDone` |

**规则**：

- 所有 API 测试必须通过封装的 HTTP 工具发起请求，禁止直接调用底层 HTTP 函数
- 请求和错误均通过统一日志工具记录

**接口示例**（PowerShell）：

```powershell
# common-http.ps1 — 通用 HTTP 请求工具（接口定义）

function Invoke-Api {
    param(
        [string]$Method = "GET",
        [string]$Path,
        [object]$Body = $null,
        [hashtable]$Headers = @{},
        [string]$ContentType = "application/json",
        [int]$TimeoutSec = $script:HttpTimeout
    )
    # 返回: @{ StatusCode; Headers; Content; Error }
}

# 可选：仅当被测系统支持流式响应时实现
function Invoke-ApiSse {
    param(
        [string]$Path,
        [object]$Body,
        [hashtable]$Headers = @{},
        [int]$TimeoutSec = $script:HttpTimeout
    )
    # 返回: @{ StatusCode; ContentType; Events; HasDone; Error }
}
```

### 2.3 通用断言校验工具

提供语义化的断言函数，失败时自动记录日志并递增失败计数。

**必须提供的断言**：

| 函数 | 职责 |
| ---- | ---- |
| `Assert-Equal` | 相等判断 |
| `Assert-NotNull` | 非空判断 |
| `Assert-Contains` | 包含判断 |
| `Assert-StatusCode` | HTTP 状态码判断 |
| `Assert-HasField` | JSON 字段存在性判断 |

**必须提供的管理函数**：

| 函数 | 职责 |
| ---- | ---- |
| `Get-AssertSummary` | 返回汇总（Pass / Fail / Total） |
| `Reset-AssertCount` | 重置计数器（每个用例执行前调用） |

**规则**：

- 每个断言函数返回布尔值
- 断言结果自动计入全局计数器
- 每个测试用例执行前必须重置计数

**接口示例**（PowerShell）：

```powershell
# common-assert.ps1 — 通用断言工具（接口定义）

function Assert-Equal       { param([string]$Name, $Expected, $Actual) }
function Assert-NotNull     { param([string]$Name, $Value) }
function Assert-Contains    { param([string]$Name, [string]$Source, [string]$SubString) }
function Assert-StatusCode  { param([string]$Name, $Response, [int]$Expected = 200) }
function Assert-HasField    { param([string]$Name, [object]$JsonObj, [string]$Field) }
function Get-AssertSummary  { }   # 返回 @{ Pass; Fail; Total }
function Reset-AssertCount  { }
```

### 2.4 统一日志打印工具

**必须支持的日志级别**：

| 级别 | 用途 |
| ---- | ---- |
| Debug | 调试信息（请求详情等） |
| Info | 正常流程（PASS、测试开始等） |
| Warn | 跳过、预期内异常 |
| Error | 断言失败、严重错误 |

**规则**：

- 所有测试脚本禁止直接使用原生输出函数，统一通过日志工具输出
- 日志级别可通过配置文件全局调整

**接口示例**（PowerShell）：

```powershell
# common-log.ps1 — 统一日志工具（接口定义）

function Write-Log {
    param([string]$Level = "Info", [string]$Message)
    # 输出格式: "{时间戳} [{级别前缀}] {消息}"
}
```

### 2.5 浏览器截图工具

本模块为 E2E 联调测试专用，封装浏览器操控 + 自动截图逻辑。

**必须提供的能力**：

| 函数 | 职责 |
| ---- | ---- |
| `Get-ScreenshotPath` | 根据用例编号和步骤序号生成标准化截图路径 |
| `Save-Screenshot` | 记录截图日志并返回路径 |

**规则**：

- 截图命名统一为 `{TC-E2E编号}-{步骤序号，3位数字补零}.png`（如 `TC-E2E-01-001.png`）
- 截图保存到用例的 `output/YYYYMMDD_HHMMSS/` 目录，生成报告时汇总到报告目录的 `pictures/` 子目录
- 实际浏览器操控由自动化框架（如 Playwright、Selenium）或 AI Agent 完成

## 3. test-api — 纯 API 接口自动化测试

### 3.1 定位

直接通过 HTTP 请求调用后端 API，验证接口契约，无需启动前端服务。

### 3.2 用例目录结构

每个 API 测试用例以独立子目录组织，目录名格式为 `TC-API-{NN}-{功能描述}/`：

- `TC-API-{NN}-{功能描述}.md` — **用例说明**（必须），描述测试目标、前置条件、预期结果
- `TC-API-{NN}-{功能描述}.{ext}` — **执行脚本**（可选），无脚本的用例仅作为文档存在
- `output/` — **执行产出**（执行后生成），按时间戳分子目录存放 `request-body.json`、`response-body.json`、`test.log`
- 总执行入口：`run-all.{ext}`（位于 `test-api/` 根目录）

### 3.3 脚本模板

每个 API 测试脚本应遵循以下结构：

```powershell
# ============================================================
# TC-API-{NN} — {测试用例名称}
# 类型: API 自动化测试
# 前置条件: {描述}
# ============================================================

param(
    [string]$BaseUrl = "",
    [string]$Credential = ""
)

# --- 引入公共依赖（强制） ---
# 路径说明：脚本位于 test-api/TC{NN}-xxx/ 二层子目录中
#   $PSScriptRoot = test-api/TC{NN}-xxx/
#   ..\..           = test/（项目根目录）
. "$PSScriptRoot\..\..\test-common\config.global.ps1"
. "$PSScriptRoot\..\..\test-common\common-log.ps1"
. "$PSScriptRoot\..\..\test-common\common-http.ps1"      # 推荐：涉及 HTTP 测试时引入
. "$PSScriptRoot\..\..\test-common\common-assert.ps1"     # 推荐：涉及断言时引入

# 参数覆盖
if ($BaseUrl)    { $script:BaseUrl = $BaseUrl }
if ($Credential) { $script:TestCredential = $Credential }

Reset-AssertCount

# --- 测试逻辑 ---
# --- Test 1: {子测试名称} ---
$response = Invoke-Api -Method GET -Path "/xxx"
Assert-StatusCode "接口返回 200" $response 200
$result = $response.Content | ConvertFrom-Json
Assert-HasField "响应包含 xxx 字段" $result "xxx"

# --- 输出汇总 ---
$summary = Get-AssertSummary
Write-Log Info "TC{NN} 测试结果: $($summary.Pass) 通过, $($summary.Fail) 失败"
exit $(if ($summary.Fail -eq 0) { 0 } else { 1 })
```

**引入规则**：

| 模块 | 要求 | 说明 |
| ---- | ---- | ---- |
| config.global | 强制 | 所有脚本必须引入 |
| common-log | 强制 | 所有脚本必须引入 |
| common-http | 推荐 | 涉及 HTTP 请求时引入 |
| common-assert | 推荐 | 涉及断言校验时引入 |

**Python/pytest 等价示例**（展示相同逻辑在其他技术栈中的实现方式）：

```python
# TC{NN} — {测试用例名称}
# 类型: API 自动化测试

import pytest
from test_common.config import load_config
from test_common.http import invoke_api
from test_common.asserts import (
    assert_status_code, assert_has_field, assert_equal
)

cfg = load_config()

class TestHealthCheck:
    """健康检查接口测试"""

    def test_status_returns_200(self):
        response = invoke_api("GET", "/health")
        assert_status_code(response, 200)
        data = response.json()
        assert_has_field(data, "status")
        assert_equal(data["status"], "ok")
```

### 3.4 run-all — 总执行入口

```powershell
# ============================================================
# API 自动化测试 — 总执行入口
# 用法: .\run-all.ps1 [-BaseUrl {后端地址}] [-Credential {认证凭证}]
# ============================================================

param(
    [string]$BaseUrl = "",
    [string]$Credential = ""
)

# 引入公共依赖
. "$PSScriptRoot\..\test-common\config.global.ps1"
. "$PSScriptRoot\..\test-common\common-log.ps1"

# 1. 检查后端服务可达
# 2. 收集测试用例（支持两种模式，按项目选择）：
#    a) 自动发现：按命名模式扫描目录，自动收集匹配 `TC*-*.{ext}` 的脚本
#    b) 手动注册：在列表中显式声明用例名称和文件路径
# 3. 依次执行，汇总结果，输出通过率
# 4. 退出码：0 = 全部通过，1 = 存在失败

# 手动注册示例（按项目实际情况维护）
# 路径为相对于 test-api/ 根目录的路径，含子目录前缀
$testScripts = @(
    @{ Name = "TC-API-01 — 健康检查"; File = "TC-API-01-health-check/TC-API-01-health-check.ps1" }
    @{ Name = "TC-API-02 — 用户登录";   File = "TC-API-02-user-login/TC-API-02-user-login.ps1" }
    # ...
)
```

### 3.5 编写规则

- 每个脚本独立可运行，也可通过 `run-all` 统一执行
- 禁止在脚本中直接调用底层 HTTP 函数
- 禁止直接使用原生输出函数，统一使用日志工具
- 每个断言必须有描述性名称（第一个参数）
- 脚本退出码：0 = 全部通过，1 = 存在失败

### 3.6 用例管理规则

每个测试用例以独立子目录聚合所有相关文件，三要素如下：

| 要素 | 要求 | 格式 | 说明 |
| ---- | ---- | ---- | ---- |
| 用例说明 | **必须** | `TC-API-{NN}-{功能描述}.md` | 描述测试目标、前置条件、预期结果、填写数据 |
| 执行脚本 | 可选 | `TC-API-{NN}-{功能描述}.{ext}` | 无脚本的用例仅作为文档留存，后续可补充实现 |
| 执行产出 | 必须（执行后） | `output/YYYYMMDD_HHMMSS/` | 每次执行后的 `request-body.json`、`response-body.json`、`test.log` |

**产出目录约定**：

- `output/` 目录在执行后自动创建，按时间戳分子目录，保留多次执行记录
- 产出文件类型：请求体（`request-body.json`）、响应体（`response-body.json`）、终端日志（`test.log`）
- `output/` 目录加入 `.gitignore`，不提交到版本库
- `test-report/` 中的汇总报告引用 `output/` 中的原始数据

## 4. test-e2e — 前后端联调测试

### 4.1 定位

通过浏览器自动化工具操控前端页面，验证前后端联调效果，每步操作截图留证。

### 4.2 用例目录结构

每个 E2E 测试用例以独立子目录组织，与 API 层规则一致：

- `TC-E2E-{NN}-{功能描述}.md` — **用例说明**（必须），描述操作步骤、预期结果、截图要求
- `TC-E2E-{NN}-{功能描述}.{ext}` — **执行脚本**（可选）
- `output/` — **执行产出**（执行后生成），按时间戳分子目录存放截图（`TC-E2E-{NN}-001.png` 等）、`request-body.json`、`response-body.json`、`test.log`
- 总执行入口：`run-all.{ext}`（位于 `test-e2e/` 根目录，调用自动化框架或 AI Agent 执行）

### 4.3 测试用例文档模板

每个 E2E 测试用例以 Markdown 文档描述，供自动化框架或 AI Agent 读取并执行：

```markdown
# TC-E2E-{NN} — {测试用例名称}

## 前置条件

- 前端服务已启动：{前端地址}
- 后端服务已启动：{后端地址}
- 测试数据：{描述需要的预置数据}

## 测试步骤

| 步骤 | 操作 | 预期结果 |
| ---- | ---- | --------- |
| 1 | 访问 {页面路径} | 页面正常加载，无报错 |
| 2 | 点击 {按钮/元素} | {预期效果} |
| 3 | 填写表单：{字段} = {值} | 表单填写完成 |
| 4 | 点击"保存" | 提示保存成功 |
| 5 | 验证列表更新 | 新记录出现在列表中 |

## 填写数据

| 字段 | 值 |
| ---- | --- |
| {字段名} | {测试值} |

## 整体期望结果

- {整体预期行为描述，区别于每步操作列中的"预期结果"}
- {跨步骤的验证条件，如"列表中不出现重复记录""接口响应时间 < 2s"等}

## 截图要求

- 每个步骤操作后截图
- 命名格式：`TC-E2E-{NN}-{步骤序号，3位数字补零}.png`（如 `TC-E2E-{NN}-001.png`）
```

### 4.4 执行规则

- E2E 测试执行前，应校验用例文档格式是否符合 4.3 节模板（前置条件、测试步骤三列表格、填写数据、整体期望结果、截图要求五个 section 齐全）
- E2E 测试由自动化框架或 AI Agent 读取用例文档并执行
- 前端和后端服务必须提前启动
- 每个步骤操作后必须截图，截图保存到当次报告目录
- 用例失败时记录原因，继续执行后续用例

## 5. 测试数据管理

### 5.1 数据准备

- 每个测试用例应自包含测试数据，不依赖其他用例的执行结果
- 需要预置数据时，在测试用例文档的"前置条件"中明确声明
- 测试数据应在配置文件中集中管理，禁止硬编码

### 5.2 数据清理

- 测试结束后应清理产生的测试数据（新增、修改的记录）
- 禁止依赖其他用例产生的脏数据
- 建议在 `run-all` 执行前后提供数据初始化/清理的钩子

### 5.3 数据隔离

- 不同环境的测试数据应隔离（开发 / 测试 / 预发布）
- 测试数据库与生产数据库必须物理隔离
- 并行执行的测试用例之间不得共享可变数据

## 6. 失败处理与重试策略

### 6.1 失败分类

| 分类 | 标记 | 说明 | 是否计入失败率 |
| ---- | ---- | ---- | ------------- |
| 环境问题 | BLOCKED | 服务未启动、网络不通等 | 否 |
| 用例失败 | FAIL | 断言不通过 | 是 |
| 用例跳过 | SKIP | 前置条件不满足 | 否 |

### 6.2 重试策略

| 测试类型 | 默认重试次数 | 说明 |
| ------- | ---------- | ---- |
| API 测试 | 0 | 快速失败，不重试 |
| E2E 测试 | 0~1 | 因浏览器不稳定，可配置 1 次重试 |

### 6.3 失败记录

- 每个失败用例必须记录：失败时间、失败步骤、期望值、实际值
- E2E 测试失败时必须保留失败截图
- 失败信息必须体现在测试报告中

## 10. 通用规则

### 10.1 命名规范

| 类型       | 格式                                  | 示例                                  |
| ---------- | ------------------------------------- | ------------------------------------- |
| API 用例目录 | `TC-API-{NN}-{功能描述}/`           | `TC-API-04-health-check/`            |
| API 用例说明 | `TC-API-{NN}-{功能描述}.md`         | `TC-API-04-health-check.md`          |
| API 执行脚本 | `TC-API-{NN}-{功能描述}.{ext}`      | `TC-API-04-health-check.ps1`         |
| E2E 用例目录 | `TC-E2E-{NN}-{功能描述}/`           | `TC-E2E-01-api-key-management/`      |
| E2E 用例说明 | `TC-E2E-{NN}-{功能描述}.md`         | `TC-E2E-01-api-key-management.md`    |
| E2E 截图    | `TC-E2E-{NN}-{步骤序号，3位数字补零}.png`      | `TC-E2E-01-001.png`                   |
| 产出日志   | `test.log`                            | `test.log`                            |
| 产出请求体 | `request-body.json`                   | `request-body.json`                   |
| 产出响应体 | `response-body.json`                  | `response-body.json`                  |
| 报告       | `YYYYMMDD_HHMMSS.md`                  | `20260613_153022.md`                  |
| 公共工具   | `common-{功能}.{ext}`                 | `common-http.ps1`                     |

### 10.2 测试用例编号

- 编号格式：`TC-{层}-{NN}`，其中 `{层}` 为 `API` 或 `E2E`，`{NN}` 为两位数字（从 01 开始递增）
- API 和 E2E 各自独立编号，无须按测试类型分段
- E2E 和 API 层描述同一功能的不同验证视角时，使用独立编号（如 TC-E2E-05 和 TC-API-05 各自独立）。编号仅表示各层内的序号，不跨层对齐
- 编号一旦分配不得复用（已删除的用例编号不再给新用例使用）

### 10.3 依赖引入

所有测试脚本必须引入配置和日志模块，按需引入其他模块：

```powershell
# 路径说明：脚本位于 TC{NN}-xxx/ 子目录中，向上跳两层到达 test/ 根目录
# 强制引入
. "$PSScriptRoot\..\..\test-common\config.global.ps1"
. "$PSScriptRoot\..\..\test-common\common-log.ps1"

# 按需引入
. "$PSScriptRoot\..\..\test-common\common-http.ps1"           # 涉及 HTTP 测试时
. "$PSScriptRoot\..\..\test-common\common-assert.ps1"         # 涉及断言时
. "$PSScriptRoot\..\..\test-common\common-screenshot.ps1"      # E2E 截图时
```

Python / Node.js 等语言的等价方式：

```python
# Python (pytest)
from test_common.config import load_config
from test_common.log import logger
from test_common.http import invoke_api        # 按需
from test_common.asserts import assert_status   # 按需
```

```javascript
// Node.js
const config = require('./test-common/config.global');
const logger = require('./test-common/common-log');
const { invokeApi } = require('./test-common/common-http');    // 按需
const { assertStatus } = require('./test-common/common-assert'); // 按需
```

### 10.4 退出码约定

| 退出码 | 含义               |
| ------ | ------------------ |
| 0      | 全部通过           |
| 1      | 存在失败用例       |

### 10.5 禁止清单

- 禁止在测试脚本中硬编码服务地址、密钥
- 禁止直接使用底层 HTTP 函数（必须通过封装工具）
- 禁止直接使用原生输出函数（必须通过日志工具）
- 禁止跳过失败用例不记录
- 禁止在报告中遗漏失败用例的截图或日志
- 禁止将 `output/` 目录提交到版本库（通过 `.gitignore` 排除）

## 11. 测试文档维护规则

### 11.1 文档职责

本规范定义测试体系的组织结构、公共工具规范、用例格式和报告模板。

```plaintext
测试设计规范.md          # 定义"怎么组织测试"
    ↓ 指导
test-common/             # 公共工具实现（按规范编写）
    ↓ 被引用
test-api/                # API 测试脚本（按规范编写）
test-e2e/                # E2E 测试用例（按规范编写）
    ↓ 执行后生成
test-report/     # 测试报告（按模板生成）
```

### 11.2 更新触发条件

| 场景 | 需更新的章节 |
| ---- | ----------- |
| 新增测试用例 | 无需更新规范文档，按现有规范编写即可 |
| 新增公共工具模块 | 第 2 章（test-common） |
| 修改报告模板格式 | 第 8 章（测试报告模板） |
| 调整测试分层架构 | 第 1 章（测试体系概览） |
| 新增测试类型（如性能测试） | 新增对应章节 |

### 11.3 一致性检查清单

定期（如每月或大版本发布前）检查以下一致性：

- [ ] 规范中的目录结构与实际 `test/` 目录一致
- [ ] 报告模板中的占位符与实际用例格式一致
- [ ] 公共工具的实际函数签名与规范文档描述一致
- [ ] 禁止清单中的规则与实际脚本实现一致
- [ ] 目录结构变更后，所有脚本的 dot-source 路径和 run-all 注册路径已验证正确
- [ ] 各测试脚本的参数声明与其 .md 说明文档中描述的前置条件一致；run-all 入口传递的参数与各子脚本声明的参数匹配

### 11.4 版本管理

- 测试规范文档不单独维护版本号，以 Git 提交记录为准
- 重大变更需在文档开头添加变更记录（可选）
- 历史规范可通过 Git 历史追溯
