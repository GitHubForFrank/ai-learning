# 测试执行规范

> 本文定义测试执行的标准流程，包括环境准备、API 测试执行、E2E 测试执行、产出收集与报告生成。
> 本文与具体项目解耦，项目仅需替换命令中的占位符（`{后端地址}` 等）即可使用。
>
> **本项目落地**：git-gui 按本模板落地为 `test-unit/`（JUnit5 + Mockito）+ `test-ui/`（TestFX），具体见 [../README.md](../README.md)。本文保留通用模板内容供跨项目复用。

---

## 1. 执行模式总览

| 模式 | 命令入口 | 前置条件 | 产出 |
| ---- | ------- | ------- | ---- |
| 全量测试 | 先执行 E2E，再执行 API | 前后端服务均已启动 | `test-report/` 汇总报告 |
| 仅 API 测试 | `test-api/run-api-tests.ps1` | 后端服务已启动 | 各 case 的 `output/` + 汇总报告 |
| 仅 E2E 测试 | `test-e2e/run-all.{ext}` 或自动化框架 | 前后端服务均已启动 | 各 case 的 `output/` + 汇总报告 |
| 单用例测试 | 直接执行单个用例脚本 | 依赖的服务已启动 | 该 case 的 `output/` |

## 2. 执行前检查清单

按执行范围勾选以下检查项：

### 2.1 环境检查

- [ ] 配置文件存在且可读（`test-common/config.global.*`）。若不存在且所有脚本参数均有默认值，标记 WARN 后继续；若脚本依赖配置文件中的值且无默认值，标记 BLOCKED。
- [ ] 配置文件中的地址和凭证已填写（非占位符状态），若仍为 `{测试用凭证}` 等占位符则标记 BLOCKED
- [ ] 敏感信息未提交到版本库（`config.local.*` 在 `.gitignore` 中）

### 2.2 服务可达性检查

- [ ] **API 测试**：后端服务地址可访问（如 `curl {后端地址}/health` 返回 200）
- [ ] **E2E 测试**：前端页面可访问 + 后端服务地址可访问

### 2.3 依赖检查

- [ ] `test-common/` 下的公共工具模块均可正常加载
- [ ] 各测试用例的 `.md` 说明文件存在（必须）
- [ ] 各测试用例的执行脚本路径与 `run-api-tests.ps1` 中注册的一致
- [ ] 执行预检：遍历 `run-api-tests.ps1` 中注册的脚本路径，逐一 `Test-Path` 确认存在。预检结果分三级处理：
  - **BLOCKED 级**（配置文件中凭证为占位符、服务不可达）：终止当前类型测试
  - **WARN 级**（脚本路径不匹配、dot-source 路径错误、缺少非必须模块）：输出警告清单后继续，但测试结果中标注"脚本执行不可用，结果来自手动验证"
  - **INFO 级**（建议性检查项未通过）：记录后继续

## 3. API 测试执行流程

### 3.1 全量 API 测试

**命令**：

```plaintext
# PowerShell
./test/test-api/run-api-tests.ps1 -BaseUrl "{后端地址}" -Credential "{认证凭证}"

# Makefile / npm scripts 等按项目自定义
make test-api BASE_URL={后端地址} CREDENTIAL={认证凭证}
```

**执行步骤**：

1. 加载 `test-common/` 下的全局配置和日志模块
2. 收集 `run-api-tests.ps1` 中注册的用例列表，**静态检查所有脚本文件存在**，任一缺失则终止并列出缺失文件
3. 检查后端服务可达（如 `/health` 端点），不可达则标记 BLOCKED 并退出
4. 按用例列表依次执行每个用例脚本
5. 每个用例执行时：
   - 加载该用例的 `.md` 说明文件确认预期行为
   - 执行测试脚本（如存在），输出保存到 `output/YYYYMMDD_HHMMSS/`
   - 失败时记录原因，继续执行下一个用例
6. 汇总所有用例的断言计数器，计算通过率
7. 按报告模板生成汇总报告，保存到 `test-report/`

**退出码**：

- `0`：全部用例通过
- `1`：存在失败用例

### 3.2 单用例 API 测试

**命令**：

```plaintext
./test/test-api/TC-API-{NN}-{功能描述}/TC-API-{NN}-{功能描述}.ps1 -BaseUrl "{后端地址}" -Credential "{认证凭证}"
```

**适用场景**：调试单个接口、验证修复、快速回归。

### 3.3 产出收集

每次执行后，以下文件自动写入用例目录的 `output/YYYYMMDD_HHMMSS/`：

| 文件 | 内容 | 最低实现要求 | 理想实现 |
| ---- | ---- | ----------- | ------- |
| `test.log` | 终端日志原文（含时间戳和断言结果） | 终端输出重定向到文件 | 日志模块自动写入 |
| `request-body.json` | HTTP 请求体 | 脚本手动 `Out-File` 写入 | HTTP 工具模块自动捕获 |
| `response-body.json` | HTTP 响应体 | 脚本手动 `Out-File` 写入 | HTTP 工具模块自动捕获 |

### 3.4 脚本不可用时的降级方案

当脚本路径预检为 WARN 级（脚本路径不匹配、dot-source 断链等）时，允许通过降级方案继续完成功能验证：

- 允许通过 HTTP 客户端（curl、Postman 等）直接调用接口完成功能验证
- 报告中必须标注"结果来自手动验证，脚本执行不可用"以及脚本不可用的具体原因
- 手动验证时仍需遵循产出收集规范（记录请求体、响应体、日志）
- 通过率统计中，手动验证的用例单独标注（如 `PASS*`），不计入脚本通过/失败统计，避免混淆脚本质量和接口质量

## 4. E2E 测试执行流程

### 4.1 执行方式选择

E2E 测试支持两种执行方式，项目按需选择：

**方式 A：自动化框架执行（推荐）**

使用 Playwright / Cypress / Selenium 等自动化框架，读取用例 `.md` 文档中的步骤表格，逐步骤操作浏览器并截图。

**方式 B：AI Agent 执行**

将用例 `.md` 文档作为输入，由 AI Agent 操控浏览器完成操作和截图。

### 4.2 全量 E2E 测试

**执行步骤**（两种方式通用）：

1. 确认前端和后端服务已启动且可访问
2. 按 `run-all.{ext}` 中注册的用例列表，依次处理每个用例
3. 每个用例执行时：
   - 读取 `TC-E2E-{NN}-{功能描述}.md`，校验用例文档格式是否合规（前置条件、测试步骤三列表格、填写数据、整体期望结果、截图要求五个 section 齐全）。不合规的用例标记为 SKIP 并记录缺失项，继续处理下一个用例
   - 按步骤表格中"操作"列的描述操控页面
   - 每步操作后截图，按 `TC-E2E-{NN}-{步骤序号，3位数字补零}.png` 命名
   - 验证预期结果，失败时记录原因
   - 所有截图和日志保存到 `output/YYYYMMDD_HHMMSS/`
4. 汇总结果，按报告模板生成汇总报告

### 4.3 单用例 E2E 测试

**方式 A（自动化框架）**：运行对应用例的脚本。

**方式 B（AI Agent）**：将单个用例 `.md` 文件作为输入上下文执行。

### 4.4 产出收集

| 文件 | 内容 | 生成方式 |
| ---- | ---- | ------- |
| `TC-E2E-{NN}-001.png` 等 | 每步操作截图 | 浏览器截图工具 |
| `test.log` | 操作日志 | 日志模块写入 |
| `request-body.json` | 请求体（如有） | HTTP 模块捕获 |
| `response-body.json` | 响应体（如有） | HTTP 模块捕获 |

### 4.5 截图规范

- 命名：`TC-E2E-{NN}-{步骤序号，3位数字补零}.png`（如 `TC-E2E-01-001.png`）
- 全页截图，不得仅截取局部区域
- 失败步骤的截图必须保留
- 截图保存到 `output/YYYYMMDD_HHMMSS/`，汇总报告中用相对路径引用
- 关键步骤（表单提交前后、列表更新前后、弹窗打开前后）建议同时保存页面快照（文本形式的 a11y tree），与截图形成交叉验证。快照文件命名：`TC-E2E-{NN}-{步骤序号，3位数字补零}.snap.txt`，与截图保存在同一目录

### 5.2 产出清理策略

- `output/` 目录加入 `.gitignore`，不提交到版本库
- 建议保留最近 5 次的执行产出，更早的自动清理
- `test-report/` 中的汇总报告作为永久记录提交到版本库

## 6. 失败处理

### 6.1 失败分类与动作

| 标记 | 场景 | 动作 |
| ---- | ---- | ---- |
| BLOCKED | 服务不可达、配置文件缺失 | 终止当前类型测试，报告中标注阻塞原因 |
| SKIP | 前置条件不满足 | 跳过该用例，继续执行下一个 |
| FAIL | 断言不通过 | 记录期望值和实际值，继续执行下一个 |

### 6.2 重试规则

- API 测试默认不重试（快速失败）
- E2E 测试可配置 1 次重试（浏览器环境不稳定时启用）
- 重试后仍失败则标记为 FAIL

### 6.3 失败记录内容

每个失败用例必须记录：

- 失败时间
- 失败步骤编号和描述
- 期望值
- 实际值
- 失败截图（E2E）

## 7. 报告生成

### 7.1 报告生成时机

- 每次 `run-api-tests.ps1` 执行完毕后自动生成
- 无论失败还是通过，均生成报告
- 报告文件名：`test-report/YYYYMMDD_HHMMSS.md`（执行开始时间）

### 7.2 报告模板

> 报告模板定义见 `测试设计规范.md` §8，本处仅引用。

每次执行测试后按以下模板生成报告，核心要素：

- 基本信息（时间、类型、环境、版本）
- 测试概览（总数、通过、失败、跳过、阻塞、通过率）
- **测试结果汇总（所有 case 的执行结果一览表，标明失败原因分类：测试脚本问题 / 后端代码逻辑问题，需要通过日志时引用文件路径）**
- 基础环境检查（后端/前端可达性、配置文件完整性、脚本路径校验、公共模块可加载性等执行前检查结果）
- API 测试结果（每个用例的状态、断言结果、说明）
- E2E 测试结果（每个用例的状态、说明、截图引用）
- 问题与建议
- 附录（终端日志原文，可选）

**完整模板**：

````markdown
# 测试报告

## 基本信息

| 项目     | 内容                                     |
| -------- | ---------------------------------------- |
| 测试时间 | YYYY-MM-DD HH:MM:SS                      |
| 测试类型 | 全量测试 / API 测试 / E2E 测试            |
| 测试环境 | 本地开发 / Docker / CI                    |
| 前端地址 | {前端地址}                                |
| 后端地址 | {后端地址}                                |
| 前端版本 | x.x.x                                    |
| 后端版本 | x.x.x                                    |

## 测试概览

| 指标     | 数值  |
| -------- | ------ |
| 用例总数 | N     |
| 通过数   | N     |
| 失败数   | N     |
| 跳过数   | N     |
| 阻塞数   | N     |
| 通过率   | xx.x% |

## 测试结果汇总

> 汇总所有测试 case 的执行结果，一目了然掌握问题全貌。失败原因分为两类：**测试脚本问题**（脚本逻辑错误、参数传递错误、断言条件写错等）和**后端代码逻辑问题**（接口返回异常、数据不一致、业务逻辑缺陷等）。

| 用例编号 | 用例描述 | 测试结果 | 失败原因分类 | 说明 |
| -------- | -------- | -------- | ------------ | ------ |
| TC-API-01 | {用例描述} | PASS | — | — |
| TC-API-02 | {用例描述} | FAIL | 测试脚本问题 | {简要说明脚本哪里写错了} |
| TC-API-03 | {用例描述} | FAIL | 后端代码逻辑问题 | {简要说明后端返回的异常表现，日志见引用} |
| TC-E2E-01 | {用例描述} | PASS | — | — |
| TC-E2E-02 | {用例描述} | SKIP | — | {跳过原因} |
| ... | ... | ... | ... | ... |

**汇总表填写说明**：
- "失败原因分类"仅在测试结果为 FAIL 时填写，从以下两项中选择：**测试脚本问题** / **后端代码逻辑问题**
  - **测试脚本问题**：脚本本身的编写错误，包括但不限于：模块引入路径错误、参数传递遗漏、断言条件写错、HTTP 请求构造有误、输出格式不符合预期
  - **后端代码逻辑问题**：后端接口返回错误或不符合业务预期，包括但不限于：HTTP 状态码非预期、响应体内容与预期不一致、业务校验逻辑有缺陷、数据持久化异常
- "说明"列：失败时简要描述现象，PASS 时可留空或填"—"
- 当某个 FAIL 用例需要查看详细日志时，在"说明"列中引用对应的日志文件路径，而不是直接复制日志内容，例如：`日志：[TC-API-02/output/20260613_193000/test.log](./TC-API-02-xxx/output/20260613_193000/test.log)`

| 前端页面可达性 | PASS / WARN / BLOCKED | 地址和响应状态 |
| 配置文件完整性 | PASS / WARN / BLOCKED | 具体缺失项 |
| 测试脚本路径校验 | PASS / WARN / BLOCKED | 不匹配的脚本清单 |
| 公共模块可加载性 | PASS / WARN / BLOCKED | 缺失的模块 |

## 问题与建议

2. ...

## 附录：终端日志

> 以下为自动化测试脚本的终端输出原文（可选）。

```plaintext

==========================================

````

**模板使用说明**：

- **测试类型**：根据实际执行范围填写"全量测试"、"API 测试"或"E2E 测试"
- **测试结果汇总**：必须在报告中提供，将所有 case 的执行结果以表格形式汇总，便于一目了然掌握问题。失败原因必须分类为"测试脚本问题"或"后端代码逻辑问题"，需要查看日志时使用文件路径引用而非直接复制日志内容
- **API 测试结果**：仅执行 API 测试时，只输出此节
- **E2E 测试结果**：仅执行 E2E 测试时，只输出此节；截图路径使用相对路径 `./pictures/`
- **问题与建议**：列出测试中发现的问题、环境限制、改进建议
- **附录**：可选，粘贴测试脚本的终端输出原文，便于回溯

### 7.3 报告中的截图引用

- E2E 截图使用相对路径：`[TC-E2E-{NN}-001.png](./pictures/TC-E2E-{NN}-001.png)`
- 报告中的 `pictures/` 目录存放该次执行所有 E2E 截图的副本或软链接
- 报告生成时将各 case 的 `output/` 截图汇总到报告目录的 `pictures/`

## 8. CI/CD 集成指南

### 8.1 基本原则

- `run-api-tests.ps1` 入口支持命令行参数化（地址、凭证等均通过参数传入）
- 退出码：0 = 通过，1 = 失败（CI 可直接据此判断流水线状态）
- 配置文件中的敏感信息通过 CI 环境变量注入

### 8.2 集成示例

**GitHub Actions**：

```yaml
- name: Run API Tests
  run: |
    ./test/test-api/run-api-tests.ps1 -BaseUrl "${{ secrets.TEST_BASE_URL }}" -Credential "${{ secrets.TEST_CREDENTIAL }}"
```

**GitLab CI**：

```yaml
api-test:
  script:
    - ./test/test-api/run-api-tests.ps1 -BaseUrl "$TEST_BASE_URL" -Credential "$TEST_CREDENTIAL"
```

**通用 Shell**：

```bash
./test/test-api/run-api-tests.sh --base-url "$TEST_BASE_URL" --credential "$TEST_CREDENTIAL"
```

### 8.3 CI 环境要求

- 运行环境已安装对应语言的运行时（PowerShell / Python / Node.js 等）
- 被测服务的地址从 CI 环境变量或 Secret 中注入
- E2E 测试需要浏览器环境（如 Playwright 需 `playwright install`）

## 9. 执行检查清单（每次执行前）

在执行测试之前，确认以下事项：

- [ ] 已阅读本次执行所涉及用例的 `.md` 说明文件
- [ ] 配置文件中的地址指向正确的测试环境
- [ ] 被测服务已启动且健康检查通过
- [ ] 测试数据已准备且隔离于生产数据
- [ ] 上一次的执行产出已归档或清理
- [ ] 已知本次执行的预期范围（全量 / API-only / E2E-only / 单用例）

## 10. 通用约束

- 所有测试执行必须通过 `run-all.{ext}` 入口或按规范的单用例入口进行，禁止手动拼接 curl 等临时命令替代
- 执行过程中产生的所有输出（日志、请求体、响应体、截图）必须保存到对应 case 的 `output/` 目录
- 报告必须包含所有用例的状态（PASS / FAIL / SKIP / BLOCKED），不得遗漏
- 敏感信息（凭证、Token）不得出现在日志、报告、截图中的明文
